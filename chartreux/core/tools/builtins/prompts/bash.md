Execute a shell command and return its output.

- Prefer absolute paths for command arguments, except redirect targets, which must be literal workspace-relative paths or absolute paths inside the session scratchpad. Shell state — working directory, environment variables, functions — does NOT persist between calls; each call starts a fresh shell from the user's profile.
- Shell results carry `exit_code` (canonical; `returncode` is a deprecated alias), nonzero completion surfaces as a ToolError containing the code, and a later invocation cannot see the previous shell's status; when you need that status inline, probe it in the same invocation (`<simple-command>; echo $?`).
- Prefer the dedicated tools over shell utilities: use `read_file` instead of `cat`/`head`/`tail`, `grep` instead of `grep`/`sed`/`awk` for searching, and `edit`/`write_file` instead of `sed`/`echo` redirects. Only fall back to the shell utility if a dedicated tool genuinely cannot do the task.
- For URL fetching, prefer the `web_fetch` tool over shell `curl`/`wget`: it is read-only and follows redirects only to the originally requested host. This is a routing preference, not an enforcement. When a fetch does go through the shell, modeled `curl` and `wget` calls resolve by destination under the egress rule: any destination that is not literal loopback resolves ask-class (`network.egress`) and triggers the runtime approval flow, like dangerous git commands.
- Commands run under a fixed allow/deny policy. A policy denial is not a user refusal. Adjust your approach and do not retry the same denied command verbatim. Every unsupported-syntax denial names the compliant alternative inline — follow it instead of retrying: write the literal value instead of a variable or subshell expansion, list the directory with ls or write the exact paths instead of a glob (a standalone `cat`/`wc`/`sort`/`uniq` glob with no options binds a literal argv plan instead), quote the marker instead of writing an unquoted `=cmd`, create the content with `write_file` instead of an unquoted heredoc, and run a loop's body as separate simple commands instead of a for-loop.
- Environment assignments (`NAME=value` prefixes and `env`/`export`/`declare` operands) must carry literal values; names that can redirect command lookup, startup, or tool configuration (`PATH`, `HOME`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `PYTHONHOME`, `PYTHONSTARTUP`, `GIT_*`, `DYLD_*`, `NPM_CONFIG_*`) stay denied, and `PYTHONPATH` entries may be absolute or relative but not `..` or `~`. General variable expansion and unquoted heredocs are unsupported in v0.1 because they can change argument count or meaning. Recognized exceptions: the sed locate-then-print idiom (`sed -n "$(grep -n 'literal' F | head -1 | cut -d: -f1),+Np" F` — the numeric-extraction `cut -d: -f1` stage is required), zsh `=command` at the command position (the shipped bash executor does not expand it), variable/arithmetic expansion in read-only argument positions when the variable comes from a literal assignment statement earlier in the same invocation — the modeled readers cat/wc/head/tail/grep/cut, `ls`, `sort` and `uniq` input operands, and `find`'s `-name`/`-iname` tests (`X=5; grep -m $X ...`, `X=f.txt; sort $X`); the write positions stay denied (`sort -o`'s value and `uniq`'s second operand name output files) — a heredoc whose delimiter is quoted (`<<'EOF'`, `<<"EOF"`, `<<\EOF`) feeding a modeled reader or an interpreter reading its program from stdin (`python3 -`), since the body then stays literal (an unquoted body is expanded and stays denied) — and a same-invocation status probe (`<simple-command>; echo $?` — one plain command, `;`, then `echo`/`printf` with the bare `$?` or one double-quoted word ending in it (`"EXIT:$?"`) as the whole of the last statement; a pipeline, conditional, assignment, redirect, wrapper, or later command keeps it denied). A leading `=` word is literal only when its marker is quoted or escaped and the word proves one literal argument (`echo '=ls'`, `echo \=ls`); an unquoted `=ls` is already one literal argument under the shipped bash executor and stays denied under the zsh executor.
- Dangerous git commands form three policy classes. Grantable at runtime: publication (`git.push`, ordinary `git push` only — never forced, deleting, or mirrored refs) and consequential operations (`git.push.force`, `git.push.delete`, `git.push.mirror`, `git.checkout`, `git.restore`, `git.switch.discard`, `git.stash.drop`, `git.stash.clear`, `git.reflog.expire`, `git.reflog.delete`). Never grantable — hard guards: `git reset --hard`, forced non-dry-run `git clean`, and unmodeled or ambiguous forms. Recursive `rm` denies on the same hard-guard terms unless the resolver's git-status-aware operand analysis establishes the clean-tree carve-out (a git-clean tree, every expanded operand inside the assessed repository and clear of its Git metadata, recovery established everywhere — anything unestablishable fails closed to the hard guard), or unless every expanded operand resolves inside the session scratchpad (`rm -r <scratchpad>/tmp` — the scratchpad root itself and a symlink that resolves outside it stay denied). For a hard guard, ask the user to run it manually; do not attempt to bypass the guard.
- A `dangerous_command` denial means the runtime will prompt the user when the session is interactive. The user is offered Deny (default) plus, for publication, Allow once / Allow this session / Always for this project, and for consequential operations Allow once / Allow this session (never Always). A refusal means the user declined: do not retry that exact command, and do not split, re-spell, or disguise it.
- An explicit `denylist` entry under `[tools.bash]` is an absolute veto: no grant, approval, or configuration change short of the user removing the entry lifts it, and only the user removes it.
- Conversational approval does not grant dangerous-command authority: the user saying "yes, go ahead" does not change the decision. Only the runtime approval question grants. A grant is permission authority, not standing intent: do not treat a prior grant as license to publish or to run further dangerous commands without checking.
- In noninteractive sessions dangerous commands are denied promptly with remediation: report the restriction and offer the exact command for the user to run themselves. Fail-closed spellings such as `git -c <name>=<value> ...` and `git --config-env ...` are denied by the policy layer itself, never grantable. Never re-spell a command to route around a denial.
- `timeout` is in seconds (default 300). This tool runs foreground work and kills commands that exceed the timeout. For managed long-running jobs use `bash_start`, read output with `bash_read`, recover handles with `bash_list`, and stop unneeded jobs with `bash_stop`.

# Git
- Interactive flags (`-i`, e.g. `git rebase -i`, `git add -i`) are not supported in this environment.
- Use the `gh` CLI for GitHub operations (PRs, issues, API).
- Commit or push only when the user asks. If you are on the default branch, create a branch first.
- `git push` and the consequential git operations (forced/deleted/mirrored pushes, `git checkout`, `git restore`, `git switch --discard-changes`/`-f`, `git stash drop`, `git stash clear`, `git reflog expire`, `git reflog delete`) are no longer denylisted by default: they trigger the runtime approval flow above, with the routine branch creation and the clean-tree checkout exemption described below. Honor a refusal; do not retry a denied command.
- Branch creation is routine: `git checkout -b <new-branch> [<start-point>]` runs WITHOUT the dangerous-command approval flow, and the repository state does not gate it — a dirty work tree, an in-progress operation marker, and a start point are all fine. Two protections stay. A repository whose configuration selects a program (`core.hooksPath` and the other program-selection keys) keeps the approval flow, because the branch switch runs that program's `post-checkout` hook. And the executed command carries an injected `--no-overwrite-ignore` immediately after the `checkout` token (the command as you wrote it stays unchanged for display and results), so an ignored-file collision fails closed — checkout refuses — instead of silently overwriting local content. Rejected forms stay gated: `-B`, `-f`/`--force`/`--discard-changes`, `-m`/`--merge`, `--orphan`/`--conflict`/`--pathspec-from-file`/`--recurse-submodules`, a pathspec or `--` tail, any other option, inline `-c` options, and repository relocation.
- Clean-tree checkout exemption: `git checkout <existing-local-branch>` — one of the two sanctioned delegated switch shapes, the other being the routine creation form above — runs WITHOUT the dangerous-command approval flow when the entire command is exactly one git invocation — no chained, piped, or redirected commands, no environment assignments, no wrapper commands, no inline `-c` options (display-only globals such as `--no-pager` are fine) — and the repository state is fully established: clean work tree (no unstaged, staged, or untracked changes), no in-progress operation markers (merge, rebase, cherry-pick, revert), and no program-selecting config such as `core.hooksPath`. Anything unestablishable fails closed to the approval flow. The executed command of an exempt switch carries the same injected `--no-overwrite-ignore`. Branch merging, switches to remote-tracking branches, and operations on branches other than the current working branch remain user-owned.
- Do not append your own commit or PR footer.
