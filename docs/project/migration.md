# Migrating from Mistral Vibe

Chartreux is an independent, local-first derivative of Mistral Vibe v2.25.5. It keeps the coding-agent workflow but deliberately narrows the hosted-product surface. This page describes the Chartreux-specific differences; consult the [changelog](changelog.md) for the release summary.

## Removed or no longer offered

- There is no Chartreux provider account flow or application-level sign-in/sign-out. MCP OAuth login and logout remain available for MCP servers.
- Configuration remains file-based; `/settings` edits curated settings. Some keys, including `subagents.max_running_subagents`, require TOML or environment overrides.
- The Vertex provider and the dedicated reasoning adapter are removed. Use a supported Mistral, generic OpenAI-style, OpenAI Responses, or Anthropic-style provider definition instead.
- OpenRouter and OpenCode Zen presets are not shipped; the OpenCode Go preset remains available.
- Extra upstream themes are gone: use `auto`, `light`, or `dark`.
- The selectable built-in `explore` subagent is gone. The built-in identities are `coder` (the neutral default child identity), `orchestrator`, `researcher`, `reviewer`, and `advisor`; the retired `explore` and `tests` prompt IDs no longer resolve, and custom identities are prompt files in `~/.chartreux/prompts/`.

## What changed

- **Credentials and onboarding.** Provider keys are supplied through environment variables or `$CHARTREUX_HOME/.env` (normally `~/.chartreux/.env`), rather than an OS-keychain onboarding flow. Setup writes ordinary settings to `config.toml` and saved providers, models, and presets to `models.toml`. A non-empty process environment value takes precedence; if it is unset or empty, Chartreux may load a non-empty `.env` value. The runtime keyring fallback is not an onboarding store.
- **Configuration and models.** `config.toml` holds ordinary settings. Provider, deployment, and role presets live in the shipped catalog plus the optional user `models.toml` overlay. Each role is one model and thinking level; it does not route among models. A canonical model can still have multiple provider deployments under the existing deployment-selection rules. See [Models](../guides/models.md) and the [configuration reference](../reference/configuration.md).
- **Subagents.** `task` runs asynchronously by default and launches child identities under purpose routes. Retained subagents can be checked, waited for, read, released, or retasked, and their transcripts can be browsed. Retention is opt-in: agents close on completion unless retained (the global `[subagents].retain_agents` default or the per-launch `retain` argument), retained idle agents are kept for `idle_ttl_seconds` (default 300) with at most `max_idle_agents` (default 4) resident, and at most 16 subagent runs can be active at once.
- **Tools and permissions.** The permission model was reworked around typed tools and server-side policy. Chartreux also adds provider-configurable `web_search` and vision-gated `read_image`; see [Tools and safety](../guides/tools-safety.md).
- **Delivery boundary.** The Textual CLI, ACP, and programmatic clients share the app-server harness and its typed public state rather than using separate live runtimes. See [ACP](../integrations/acp.md) and [the app server](../integrations/app-server.md).
- **Shell policy breaking change.** The recognized dangerous git operations (`git push`, `git checkout`, `git restore`, `git stash drop`, `git stash clear`, `git switch --discard-changes`, `git switch -f`, `git reflog expire`, `git reflog delete`) left the shipped `[tools.bash]` denylist and are now governed by typed runtime approval: interactive sessions prompt the user (Deny default), noninteractive sessions deny with remediation, and only ordinary `git push` is persistable ("Always for this project"). Explicit denylist entries remain an absolute veto, and `denylist = []` no longer implicitly authorizes these commands — publication now requires a grant. Hard guards (`git reset --hard`, forced non-dry-run `git clean`, recursive `rm` outside its clean-tree carve-out) remain denied with no grant path. See [dangerous git commands](../guides/tools-safety.md#dangerous-git-commands).

## Configuration migration

1. Move provider credentials to the environment or `$CHARTREUX_HOME/.env`; do not depend on an interactive account session.
2. Set the main assistant default through `[roles.main]` in `models.toml`; `active_model` and persisted `thinking_overrides` in `config.toml` are rejected. Use `/model` and `/thinking` for session changes. Use `CHARTREUX_*` variables for other supported environment overrides; nested fields use `__`.
3. Move legacy provider/model catalog tables out of `config.toml`. Run `chartreux models migrate` to preview, then `chartreux models migrate --apply` to create a backup and write `models.toml`.
4. Replace retired provider styles and presets with explicit supported provider definitions in `models.toml`. Retired configuration keys fail validation rather than being silently translated.
5. Replace retired `[tags]` tables, model `aliases`, and ordered role `models` lists with presets. Define each role as `[roles.<name>]` with one `model` and `thinking`; select it with `@<name>`. Launch separate tasks for parallel work; `fan_out: true` is rejected.
6. Recheck tool permissions and MCP configuration. Remote MCP transport is `streamable-http`, local process transport is `stdio`; the old `http` spelling is rejected.

Chartreux combines configuration in this order: defaults, user TOML, trusted project TOML, `CHARTREUX_*` environment values, then session overrides; the `[agent]` identity/workflow/orchestration-strategy selections resolve CLI > environment > config > shipped default. Project configuration can select catalog entries but cannot define the catalog.

## Agent setup migration

The identity rework replaced the profile/slot/prompt-ID axes with `[agent]` selections and purpose routes, with no automatic migration: `chartreux models migrate` covers only the model catalog, and `chartreux doctor` reports the retired settings with successor guidance but translates nothing. Translate a pre-identity agent setup by hand:

1. **Main-agent prompt selection** (a `system_prompt_id` such as `orchestrator`, or a full-skeleton replacement prompt): select the built-in through `[agent] identity = "orchestrator"` in `config.toml` or `--identity orchestrator` per invocation. Reserved built-in names (`coder`, `orchestrator`, `researcher`, `reviewer`, `advisor`) cannot be shadowed by user prompt files, so an old `prompts/orchestrator.md` is inert — delete it. Acceptance-gate ceremony that used to live in a custom skeleton prompt now lives in the shipped `ceremony` workflow: select it with `[agent] workflow = "ceremony"`.
2. **`agents/*.toml` profiles**: the directory convention is retired; files are detected and reported by `chartreux doctor` but never loaded, and profile-level `retain` and idle-TTL settings are gone. Recreate each profile's model binding as an `[orchestration.routes.<purpose>]` target (for example, a high-thinking implementation worker becomes a `targets = [{ model = ..., identity = "coder", tier = "substantive" }]` entry), and keep retention as the global `[subagents]` default plus the per-launch `retain` argument.
3. **Worker prompt bodies**: a custom worker prompt file in `~/.chartreux/prompts/` still resolves as a custom identity (`user:<stem>`, or the bare stem) and can be referenced from a route target's `identity` field or a `task` launch. The shipped bounded-child contract already carries the disclosure, denial-record, and touched-path rules, so a custom worker prompt only needs to add what the shipped fragment lacks.
4. **Older selection keys** (`agent_paths`, `enabled_agents`, `disabled_agents`, `[dispatch]`): retired. `doctor` names each with its successor; block launchable identities with `tools.task.denylist` and configure routing through `[orchestration.routes.*]`.

## Upgrading from 0.5.8

The v0.6.0 permission realignment changes what the shell resolver allows, what it asks about, and where authority lives. What a user upgrading from 0.5.8 will experience differently:

- **Destination-aware egress (the settled exfiltration decision).** Modeled `curl` and `wget` calls are no longer denylisted outright; their destinations decide. Literal loopback destinations (`localhost`, `127.0.0.0/8`, `::1`) run with no dialog; any other destination — another IP literal, a DNS name, or one the recognizer cannot parse — resolves ask-class (`network.egress`) and prompts in interactive sessions, denies with remediation in headless and child sessions. Redirect-following flags (`curl -L`), `wget`'s default redirect behavior, and destination-overriding options (`--resolve`, `--connect-to`) resolve ask-class even for a loopback URL. `git fetch`/`clone`/`pull` and `pip`/`uv` installs stay run-class. A user denylist entry for these clients remains an absolute veto.
- **Probed egress clients move onto the shipped denylist.** `ssh`, `scp`, `rsync`, `ftp`, `telnet`, `http`/`httpie`, `wget2`, `aria2c`, `lftp`, and `watch` are denied by the shipped default denylist until they are modeled; remove an entry to re-enable a client deliberately.
- **Recursive `rm` gains a git-clean carve-out.** Over a tree with unsaved changes the blanket hard-guard denial remains. Over a git-clean tree a recursive `rm` runs on its own only when every expanded operand lies within the assessed repository, clear of its Git metadata (including linked-worktree common directories), with recovery established for every repository involved, nested ones included; anything unestablishable and any mixed operand fails closed to the hard-guard denial. See [Recursive rm analysis](../guides/tools-safety.md#recursive-rm-analysis).
- **Wrapper and builtin modeling.** `sg` and `sudo -u <user>` are transparent wrappers whose payloads are re-analyzed (`sg`'s unquoted multi-token `-c` payloads included); `git symbolic-ref` resolves in read mode and is classified by mode; `.venv/bin/python --version` resolves while bare `.venv/bin/python` stays denied; a `VIRTUAL_ENV=...` prefix no longer denies. See [Wrapper and flag recognition](../guides/tools-safety.md#wrapper-and-flag-recognition-v060).
- **Project environment injection.** Inside a trusted folder, the project `.env` and `$CHARTREUX_HOME/.env` load into `bash`/`bash_start` subprocess environments, with known secret values masked in tool output; document expected key names in a committable `.env.example`. See [Project environment injection](../guides/configuration.md#project-environment-injection).
- **Artifact secret scan.** A gitleaks-style scan over the session's touched paths gates agent submissions (the submission is blocked and the finding is redacted) and runs as a pre-commit hook for user-driven commits. See [Artifact secret scan](../guides/tools-safety.md#artifact-secret-scan).
- **Local tool trust.** Tools authored under `~/.chartreux/tools/` are trusted by file location and admitted to the non-mutating posture; project-discovered tools, `tool_paths` entries, and MCP proxies stay fail-closed. The provenance-stamp machinery is removed; shipped builtins are classified by their defining module. See [Local tool trust](../guides/tools-safety.md#local-tool-trust).
- **Live route editing.** Route edits now apply to subsequent launches in the same conversation (previously they applied to new conversations only); in-flight children keep their admitted bindings, and a resumed conversation adopts the current saved table with a diff notice. See [ADR 0022](../adr/0022-live-route-editing.md).
- **Child sessions deny ask-class outright.** A child session never surfaces the dangerous-command approval dialog, regardless of user-input capability; a denied ask-class call returns a blocker to the parent, and `dangerous_command_grants_by_project` is the only child pre-authorization path. Saved project grants still run in children without a prompt.
